= Changelog

== Unreleased

* *Fixed — brand buttons on the chooser* (#8). Every redirect provider was rendered as its
  bare brand name in a generic bordered box. For Google that is the one rendering its
  guidelines explicitly forbid — and Boot's `CommonOAuth2Provider.GOOGLE` sets the client
  name to exactly `Google`, so every consumer enabling a Google registration inherited it.
  Facebook had the same problem, which the issue did not mention: its guidelines name the
  two labels it accepts and the brand name alone is not one of them.
+
Each brand now carries its required wording and mark — the full-colour G and Microsoft's
four squares, which both forbid alteration, and the official black or white variants of the
GitHub, Facebook and Apple marks, switched by theme rather than recoloured. The labels read
alike as far as the guidelines allow; identical wording is unreachable, because Microsoft's
approved set has no "Continue with" and Facebook's has no "Sign in with", so one phrasing
is used everywhere it is permitted and Facebook takes the closest label it allows.
+
The wording resolves in the model, as `AuthProvider.buttonLabel()`, not in the markup. An
application overriding `templates/uniauth/login.html` is the supported re-skin path and the
webapp example takes it, so compliance written into the template would be lost by exactly
the applications most likely to restyle the page. One deliberate deviation: Google asks for
Google Sans Medium and the starter keeps the system stack, because the chooser renders
before anybody has authenticated and a webfont would make an external request on it.

* *New artifact — `uniauth-spring-boot-starter-test`* (#37). A durable `ApprovalStore` or
  `InvitationStore` is the application's job by design, and its correctness rules lived only in
  prose — so every implementor rediscovered them alone, including the one that cannot be found
  by reading code: `redeem` must be a compare-and-set, and a read-then-write passes every
  single-threaded test while binding two people to one record under load.
+
`InvitationStoreContract` and `ApprovalStoreContract` are suites an implementation extends by
supplying its store. The clock handed over is mutable, so an implementation that reads it once
in its constructor is caught. A module of its own rather than a tests-classifier jar on the
starter: a test-jar would publish every internal test class, making `TestApplication` and
200-odd tests de facto API.
+
The suites are themselves run against deliberately broken stores to prove they fail them,
which is the part a contract kit usually lacks. That exposed something worth documenting: of
the five cases touching revocation, three still pass against a store that ignores `revoke`
entirely, because they assert what revocation leaves alone. Passing is evidence, not proof.
* *Docs — `ApprovalStore.decide` signature was stale* in `approval.adoc`, missing the `roles`
  parameter an implementor copies.

* *New — a hook on `HttpSecurity` itself* (#12), `UniAuthHttpSecurityCustomizer`. The chain is
  built inside the starter and offered one reach into it: authorization rules. Nothing answered
  CSRF, headers, CORS or session management — and since the starter configures no CSRF, Spring
  Security's session-backed default applies, so enabling UniAuth turned a front end's working
  POSTs into 403s with nothing logged. Applied after everything the starter configures, so an
  application's setting wins; a customizer that throws fails the context rather than serving a
  chain nobody asked for. A new reference page carries the single-page recipe, including the
  part that is easy to get wrong: Spring's default handler masks the token it renders, so a
  front end echoing a raw cookie value back is refused with the same 403. Closes #32, which
  asked for the same hook from the sign-out side.
* *New — `InvitationStore.findByUsedBy`* (#36). `Invitation.usedBy` already made the link
  between a login and the record it claimed durable, but the only way to ask was to list every
  invitation and filter. A `default` method, so no existing implementation changes; the latest
  claim wins, and a claim later revoked is still returned, because that is the one whose link
  needs attention.
* *Contract — `ApprovalStore.decide` on an unknown key* (#35). The interface did not say whether
  a record may be created, so an implementor could not tell which behaviour was required. It is
  now stated: the key is left alone, and pre-approving somebody before their first login is
  `recordPending` then `decide`. `InMemoryApprovalStore` gained the test suite it never had.
* *Docs — `uniauth.enabled=false` does not mean "no security"* (#33). Several pages said the
  starter "backs off entirely", which is true of the starter and misleading about the
  application: Boot's own security auto-configuration takes over and locks every path behind a
  generated password. Now stated, with the permit-all chain for an application that wants none,
  and pinned by a test.
* *Docs — a customizer rule can skip the approval gate* (#34). Rules contributed through
  `UniAuthAuthorizationCustomizer` run before the catch-all that carries the gate, so one ending
  in `.authenticated()` admits every account the provider will issue, approved or not. The
  documentation demonstrated exactly that ending; it now warns, and shows the two safe ones.
* *Docs — who creates the first invitation* (#35). `invite-only` looks as though it locks
  everyone out. It does not on the default `require-for`, which excludes internal accounts, so a
  local account is the break-glass route — and adding `INTERNAL` to `require-for` closes it,
  which is now documented along with the direct-admission recipe.

* *New — invitations* (#29), `uniauth.approval.invitations.enabled`. The approval gate needs a
  stranger to turn up first. Invitations are the other order: the application already holds a
  record for somebody, and a one-use URL attaches whichever login they complete to that
  record. A token rather than a matched email address, which removes `email_verified`, address
  normalisation, cross-provider matching and the whole disclosure question — and makes SAML and
  LDAP work as well as OIDC. Redemption happens in `ApprovalAuthorizationManager`, the one
  place every request passes exactly once, so one implementation covers all four mechanisms.
  `InvitationRedeemedEvent` is the linking contract and a listener that throws fails the
  admission, because admitted-but-unlinked is worse than "try again"; one-use is keyed by
  principal so that failure can be retried rather than stranding the invited person.
  `invite-only` refuses an uninvited principal outright instead of telling somebody who will
  never be admitted to keep waiting.
+
Opening an invitation URL only renders a page; accepting is a `POST`, because a `GET` cannot
carry a CSRF token and a `GET` with a side effect here could be fired from any other site to
plant its invitation in a visitor's session. Revoking an invitation, and a refusal an
approver recorded, both outrank the retry — the window that retry opens can be as long as an
outage, which is exactly when somebody intervenes — as does any decision an approver
recorded, including an approval whose roles are narrower than the invitation's. Re-inviting is
how an administrator changes what somebody was granted, since invitations are never reopened.
+
`InvitationRedeemedEvent` is at-least-once and the listener must be idempotent: two requests
on one session can both claim and both publish, and a listener that throws refuses the
admission. Redemption runs whether or not the mechanism is covered by
`uniauth.approval.require-for` — an invitation is not a gate — and the roles it grants reach
the principal on the request that granted them.

== 4.1.0.3

* *Fix — the Basic challenge no longer reaches a browser's XHR* (#13). `Accept` cannot tell a
  page's `fetch()` from a program, because neither asks for HTML. Every background request from
  an expired session was therefore answered with `WWW-Authenticate: Basic`, and the browser
  opened its native credential dialog *above* the page — where the application's own 401
  handling could never reach it, which is the opposite of what `uniauth.http-basic.paths`
  exists to prevent. Browsers are now identified by the `Sec-Fetch-*` headers they send on
  every request and programs do not: a navigation gets the chooser, an XHR gets a bare `401`,
  and only a caller that did not identify itself is challenged. `curl -u` and HTTP libraries
  that present credentials up front are unaffected, since they never waited for a challenge.

== 4.1.0.2

* *New — `UniAuthAuthorizationCustomizer`* (#3). The single chain offered exactly one
  authorization shape — permitted paths, then authenticated — so an application whose rules
  used roles, HTTP methods, or anything not expressible as a path string had no way in. The
  escapes were replacing the chain, which costs every mechanism, or adding a second one, which
  separates the rules from the mechanisms that satisfy them. Contribute a bean instead; it is
  applied before the catch-all, since the first matching rule wins.
* *New — HTTP Basic* (#4), `uniauth.http-basic.enabled`. The three login mechanisms all assume
  a browser and a session, leaving smoke checks, polling workers and `curl` with no way to
  authenticate. Off by default. A browser still gets the chooser rather than a native
  credential dialog, and `paths` scopes the challenge to where machines call.

* *Approving now grants roles* (#5). Approval was a boolean, so a federated principal cleared
  the gate and was then refused by every `hasRole(...)` rule in the application — it arrives
  with `OIDC_USER` and `SCOPE_*` and no `ROLE_` at all, while an internal account had roles
  from configuration all along. `ApprovalStore.decide` takes the roles the approver granted,
  `uniauth.approval.default-roles` supplies a default, and the sample's queue offers a field
  for them. They reach the principal on the next request, without a second sign-in, and the
  authentication is rebuilt keeping its concrete type so mechanism resolution still works.
  *Breaking* for anyone implementing `ApprovalStore`.

* *Breaking — `uniauth.enabled` now defaults to `false`* (#6). The starter installed its
  catch-all chain on the strength of being on the classpath, so adding the dependency changed
  an application's authorization in every profile and every test before any integration was
  written — and since the chain's default is `anyRequest().authenticated()`, the symptom was a
  broadly-locked application rather than an obviously broken one. Set `uniauth.enabled: true`
  to opt in, consistent with `internal`, `ldap` and `approval`, which already defaulted to off.
  When the chain installs it now logs so at INFO, naming its default rule and permitted paths.

* *Fix — the LDAP jars are optional again* (#2). They were compile-scope, so every consumer
  carried them; their presence activates Boot's own `LdapAutoConfiguration`, which health-checks
  `ldap://localhost:389` and reports `DOWN`. An application using Google and a local admin, with
  no directory at all, failed its Kubernetes readiness probe because of an authentication
  library — and neither `uniauth.ldap.enabled=false` nor `uniauth.enabled=false` could switch it
  off, because the indicator is Boot's and keys off the jar. Applications that use LDAP now add
  `spring-boot-starter-ldap` themselves, which is the ordinary starter pattern.

* *Breaking — SAML is an optional dependency too* (#2). It was the more expensive half: OpenSAML
  is not published to Maven Central, so a transitive dependency on
  `spring-boot-starter-security-saml2` obliged *every* consumer to declare the Shibboleth
  repository — including the ones who would never speak SAML, and with nothing in the resolution
  failure to explain why an authentication library wanted them to trust a third-party Maven
  repository. Making it optional meant nothing general could name a SAML type, so the redirect
  mechanisms now sit behind an internal `RedirectMechanism` contributor resolved by
  `@ConditionalOnClass`: `AuthProviderRegistry` and the filter chain aggregate, and
  `SamlMechanism` owns the repository, the registration type and `saml2Login`/`saml2Logout`.
  `MechanismResolver` and `PrincipalIdentityResolver` isolate the two types they read off a
  principal in nested classes, the same technique LDAP already used. *Breaking* for applications
  that use SAML: add `spring-boot-starter-security-saml2` and the Shibboleth repository to your
  own build.

== 4.1.0.1

First release. The version tracks the Spring Boot line it builds against — `4.1.0` — with a fourth
segment as this library's own patch counter.

=== Authentication

* *One `SecurityFilterChain` for four mechanisms.* Form login, OAuth2/OIDC login and SAML login are
  installed onto a single chain. Chains match in order and the first match wins, so a chain per
  mechanism would leave all but the first unreachable.
* *Internal user store* (`uniauth.internal.*`) — accounts declared in configuration, for a first run
  and for break-glass access beside a directory.
* *LDAP* (`uniauth.ldap.*`) — bind authentication with a group search, including
  `manager-dn`/`manager-password` for directories that are not world-readable.
* *OAuth2 / OpenID Connect and SAML 2.0* — consumed from Spring Boot's own
  `spring.security.oauth2.client.registration.*` and `spring.security.saml2.relyingparty.*` rather
  than re-declared under `uniauth.*`.
* *Provider chooser* — `AuthProviderRegistry` answers what a user can sign in with right now; served
  as a page and as JSON at `uniauth.providers-endpoint`.
* *`AuthProvider.oidc()`* distinguishes OpenID Connect from plain OAuth2, derived from the `openid`
  scope. This is the capability that changes what an application receives — an `OidcUser` with claims
  versus a bare `OAuth2User` — and is separate from brand.

=== Approval gate

* *`uniauth.approval.*`* inserts a decision between authenticating and being admitted. It sits in
  authorization rather than authentication, so a held principal is not reported as a credentials
  failure — which would be misleading and would confirm a correct guess to an attacker.
* *`ApprovalStore` SPI*, so the only stateful thing in the library does not force a schema on every
  consumer. `InMemoryApprovalStore` is the default and is not production-fit: it empties on restart
  and is per-instance.
* *`PrincipalIdentity` captured at first sighting* — display name, email, and whether the provider
  says it *verified* that address. Approval is keyed on the stable subject, which for an OIDC login
  is an unreadable number; the identity is what makes the decision about a person rather than about
  a key. Verification has three states, never collapsed into two: verified, unverified, and "the
  provider said nothing".

=== Provider adapters

* *`uniauth.oauth2.github.fetch-email`* — GitHub does not volunteer an email address, so this makes
  the second call that fetches one. It takes the account's *primary verified* address in preference
  to the public profile field, and reports it as verified.
* *`uniauth.oauth2.microsoft.multi-tenant`* — accepts tenant-template issuers without reimplementing
  ID token validation: Spring's own validator is given a registration copy with the issuer removed,
  keeping every other check intact, and the issuer rule is applied separately.
* Apple is deliberately unsupported while Spring requires a static client secret.

=== Extension points

* `uniauth.public-paths` for routes reachable without a session.
* An `AuthenticationEntryPoint` bean, used in place of redirecting to the chooser — this is how an
  API-first application answers `401`.
* A second `SecurityFilterChain`: the starter's catch-all backs off on its own bean *name*, so adding
  a chain no longer costs every mechanism.
