= Invitations
:description: Admitting a named person before their first login.

The approval gate answers "somebody logged in; do we let them in?". A stranger has to turn
up first, and somebody has to notice.

Invitations are the other order. The application already holds a record for Jane, with no
way to sign in; an invitation is a one-use URL that attaches whichever login she completes
to *that record*. This is account claiming, not user provisioning — the record exists, the
login does not.

[source,yaml]
----
uniauth:
  approval:
    enabled: true                 # <1>
    invitations:
      enabled: false
      path: /invite/{token}       # <2>
      default-expiry: 14d
      invite-only: false          # <3>
----
<1> Required. Redemption writes an approval record, so invitations without the gate have
    nowhere to put their decision — switching them on alone wires nothing.
<2> Must contain `{token}`. Validated at startup, because without it every invitation
    would 404 with nothing saying why. The starter permits this path on its chain: an
    invitation has to work before anybody has logged in.
<3> With this on, an uninvited principal is refused outright — a plain 403 rather than the
    waiting page. Telling somebody who will never be admitted to keep waiting is a lie.

[#the-first-administrator]
=== Who creates the first invitation

Somebody has to be inside to mint one, and `invite-only` looks like it closes that door. It
does not, on the default configuration — but the route is worth knowing before you need it
(#35).

`uniauth.approval.require-for` excludes `INTERNAL`, on the reasoning that writing an account
into configuration is already a deliberate act of approval. The `invite-only` refusal sits
*behind* that check, so an account in `uniauth.internal.users` is admitted without ever
being asked for an invitation:

[source,yaml]
----
uniauth:
  internal:
    enabled: true
    users:
      - username: admin
        password: "{bcrypt}$2a$10$..."
        roles: [ADMIN]
----

That is the same break-glass pattern the admin console uses for when the provider is down,
and it is the answer to "who invites the first person".

[WARNING]
====
Adding `INTERNAL` to `require-for` closes it again. Then every mechanism is gated, every
uninvited principal is refused, and there is nobody left who can invite anybody — a
locked-out deployment with no route back that does not involve a restart.

If you need that configuration, admit the first administrator directly instead, which
`ApprovalStore` supports as a recipe rather than a special case:

[source,java]
----
ApprovalKey key = new ApprovalKey("internal", "admin");
approvals.recordPending(key, PrincipalIdentity.ofName("admin"), AuthProviderType.INTERNAL);
approvals.decide(key, ApprovalStatus.APPROVED, "bootstrap", List.of("ADMIN"));
----

`recordPending` first is not optional: `decide` leaves a key the store has never seen
untouched, deliberately, so that a decision always has an identity and a mechanism behind
it for whoever reads the queue later.
====

`default-expiry` must be positive, and is checked at startup for the same reason the path is:
expiry is inclusive, so a zero or negative value would make every invitation born already
expired, with the store, the endpoint and the log all agreeing nothing was wrong. Omit it
entirely to mean never.

== The flow

. An administrator calls `InvitationStore.create(subjectRef, ttl, roles, createdBy)` and
  gets back an `Invitation` carrying its token.
. They deliver the URL however they like. Sending it is out of scope — the application or a
  person does that.
. Jane opens it and sees what she is accepting. Accepting is a `POST`, and that is what
  puts the token on her session — see <<the-url-is-the-credential>>.
. She signs in with Google, or the directory, or anything else enabled. An ordinary round
  trip.
. Her first authenticated request passes through `ApprovalAuthorizationManager`, which
  claims the invitation, publishes `InvitationRedeemedEvent`, and records her as
  `APPROVED`.
. The application's listener links `(google, sub)` to Jane's record.

She never sees a waiting page.

== Why a token and not an email address

Matching on the invited address drags in `email_verified`, Gmail dots and plus-tags, case
folding, "the same address from another provider must not be admitted", and a
non-disclosure rule so an uninvited login cannot reveal whether an address is invited.

A token removes all of it. The token *is* the proof, so there is nothing to normalise and no
verified-claim problem — which is also why this works identically for SAML and LDAP, where
email matching could not: `PrincipalIdentity.emailVerified` is a nullable `Boolean` precisely
because SAML carries no equivalent and GitHub may report no address at all. Disclosure stops
mattering too: whoever holds the token already holds the invitation, so telling them it has
expired is a service rather than a leak.

The cost is that the invitation has to survive the redirect out to the provider and back. It
rides the session, because the alternatives are per-mechanism — OAuth2 `state`, SAML
`RelayState`, form login neither — and three implementations of one idea is the split the
single chain exists to avoid.

[#the-url-is-the-credential]
== The URL is the credential

Whoever holds the link gets the record it names. That is inherent to link invitations and no
design removes it.

What the starter does is make it deliberate. Opening the URL only shows a page; accepting is
a `POST`. Somebody already signed in is told which account they would be accepting as — "you
are signed in as bob@example.com; accept as bob@example.com?" — and somebody not signed in is
told to accept and then sign in. Either way a mis-sent link opened by the wrong colleague is
a decision somebody made rather than something that happened.

WARNING: The `GET` must stay free of side effects, and the acceptance must stay a `POST`.
A `GET` cannot carry a CSRF token, so a `GET` that stashed the invitation could be fired from
any other site — an `img` tag is enough. It would plant that site's invitation in a visitor's
session; the visitor would then sign in with their own account and be bound to the record
that invitation names, with its roles, having never seen the page that exists to make exactly
this deliberate.

The page is also the recovery path when a session is lost mid-login, which happens: sessions
are in memory, which is why the deployments are `Recreate`. The invitation is still
unclaimed, so reopening the URL and accepting claims it without a second sign-in.

NOTE: One risk the `POST` does not close, because it is not CSRF. The token rides the session,
and Spring's default `changeSessionId` fixation protection *preserves* session attributes — so
anyone who can set a visitor's session cookie (subdomain cookie injection, or any XSS on the
domain) can accept their own invitation, plant that session id, and have the visitor's next
login bound to their `subjectRef`. `sessionFixation().newSession()` drops it, and also breaks
the ordinary flow, silently. This is inherent to carrying the token in the session, and the
defence is the one that protects every other session on the domain.

TIP: An application that overrides `templates/uniauth/login.html` — the supported re-skin
path — must render the `invite` model attribute, or every outcome below is swallowed and the
person gets a login page with no explanation.

== One use means one person, not one request

`InvitationStore.redeem` is keyed by principal. Claiming again with the *same* key succeeds
and is a no-op; claiming with a different one fails.

This matters because of what happens when the application's listener throws. The event is
published synchronously inside the authorization decision and *a listener that throws fails
the admission* — the principal stays pending and the request is refused. Admitted-but-unlinked
would be worse: the person would be browsing as nobody, holding a session no record backs.

If the claim made the token dead, one transient failure would strand Jane with a URL that can
never work again. Instead her next request redeems as a no-op and she is admitted the moment
the application recovers. The risk one-use actually guards against is a *second person*
claiming the record, and that is exactly what it still guards against.

Two things outrank that retry, because the window it opens can be as long as an outage and
that is exactly when somebody intervenes:

* *Revoking the invitation* refuses it even to the principal who already claimed it.
* *Any decision a person recorded* stands — a refusal, and equally an approval. A claim whose
  listener threw leaves precisely the pending record an approver acts on, and the retry does
  not replace their decision or the roles they chose to grant, which may be narrower than the
  invitation's.

Two decisions are not a person's and are therefore replaceable: `invite-only`'s own automatic
refusal (under that setting every stranger is recorded `DENIED`, so somebody who signed in
before opening their link would otherwise be locked out for good), and a grant an earlier
invitation made. The second is what lets an administrator *re-invite* somebody to change what
they were granted — invitations are never reopened, so a fresh one is the only way.

== Linking, with or without a listener

[source,java]
----
@EventListener
void onRedeemed(InvitationRedeemedEvent event) {
    people.linkLogin(event.subjectRef(), event.key());   // (google, sub) -> Jane
}
----

IMPORTANT: *The event is at-least-once, so the listener must be idempotent.* Two authorized
requests on one session can both read the stashed token before either clears it — the normal
shape of a browser landing on a page, not just a double-click — and the same-principal no-op
in `redeem` is what lets the second through, so both publish. A listener doing a plain
`INSERT` would get a duplicate-key exception on the second delivery, and by the contract above
that *refuses the admission* of somebody who is in fact approved.

The link is durable without any listener at all: `Invitation.usedBy` records which
`ApprovalKey` claimed which `subjectRef`, permanently, and `InvitationStore.findByUsedBy`
asks it directly:

[source,java]
----
String held = invitations.findByUsedBy(key).map(Invitation::subjectRef).orElse(null);
----

That is the question an application has on a later request, or when repairing its own link
table after a listener failed. Two edges are contract: the *latest* claim wins, because
re-inviting is how an administrator changes what somebody holds and leaves two invitations
naming the same principal; and a claim that was later *revoked* is still returned, because
revocation outranks use in `status()`, so filtering on `USED` would answer "holds nothing"
for precisely the person whose link needs attention. Check `status(now)` on what comes back.

It is a `default` method over `list`, so an existing implementation keeps compiling; one
backed by a database should override it with the indexed query rather than listing the
table. That is why `ApprovalRecord` gains no `subjectRef` field — widening it
would break every `ApprovalStore` implementation, which it already did once.

== Roles

An invitation carries roles, and falls back to `uniauth.approval.default-roles` when it names
none.

This is not optional detail. A federated principal arrives with `OIDC_USER` and `SCOPE_*` and
no `ROLE_` at all, so an approval granting nothing admits somebody who is then refused by
every `hasRole()` rule in the application — a working sign-in that reaches nothing, which
reads as a broken application rather than as a permissions decision.

== Redemption does not wait for the gate

`uniauth.approval.require-for` decides which mechanisms are *held*, and it excludes internal
accounts by default. Redemption runs before that check, because an invitation is not a gate:
it says who a login belongs to, and the application wants that link whichever mechanism
answered. Behind the check, an invitation completed with an internal login would claim
nothing, publish nothing and record no `usedBy` — while letting the person in, so neither they
nor whoever invited them would have any sign it had failed.

The roles the invitation grants are put on the principal by the authorization decision itself,
not by the filter that carries an approver's roles. That filter runs *before* authorization —
it has to, or an approver's roles would arrive after the decision that needed them — so for an
invitation it has already run by the time the roles exist. Without that, the invited person
would land on their first `hasRole`-gated page, get a 403, and find it worked on refresh.

== Any provider may redeem

An invitation names *who* may come in, not *how* they must authenticate, so it carries no
provider field. The gate's keys are `(provider, principal)`, so the resulting approval is
scoped to whichever provider answered. A deployment that later needs an invitation pinned to
one provider gets an optional field, not a redesign.

== When a link does not work

An unusable token redirects to the chooser with a reason — `?invite=unknown`, `used`,
`expired` or `revoked` — which the login template renders as one line.

Deliberately not a page of its own. The starter once redirected to a page it did not serve
and a consumer got `ERR_TOO_MANY_REDIRECTS`; an `outcome-page` property would be that mistake
with a new name. The chooser already exists and is already served.

== The store

`InvitationStore` is an SPI, on the same bargain as `ApprovalStore`: UniAuth owns the flow and
never the table. `InMemoryInvitationStore` is the default so the flow works out of the box,
and it is *not production-fit* — invitations are lost on restart, nothing is shared between
instances, and an admin console pointed at it sees only the invitations created in its own
process. The starter says so once at startup rather than refusing to run, because durability
is the deployment's choice.

One method carries a contract an implementation can break silently:

TIP: `redeem` must be a compare-and-set, not a read-then-write. A read-then-write passes
every single-threaded test and admits two people under load.

Unlike `ApprovalStore`, this interface can enumerate from the start. An administrator cannot
manage invitations they cannot list.
