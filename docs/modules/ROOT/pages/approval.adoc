= Approval gate
:description: Authenticating and being let in are separate decisions.

An identity provider will happily vouch for anyone who holds an account with it. That is its
job, and it is not the same question as whether this application should admit them. The
approval gate makes the second question explicit.

[source,yaml]
----
uniauth:
  approval:
    enabled: true
    require-for: [ LDAP, OAUTH2, SAML ]   # <1>
    pending-page: /pending
----
<1> Which mechanisms are held, and already the default. Internal accounts are left out
    because writing one into configuration is already an approval.

A held principal authenticates successfully and then lands on the pending page until an
administrator decides. Approving admits them on their next request — no second sign-in.

The gate assumes a stranger arrives first. For the other order — the application already
holds a record for somebody and wants to hand them a way to claim it — see
xref:invitations.adoc[invitations].

== Three decisions worth not re-litigating

*It sits in authorization, not authentication.* `ApprovalAuthorizationManager` replaces
`.authenticated()` in the chain. Failing the login instead would report "pending" as a
credentials failure, which is both misleading and a disclosure: it confirms a correct guess
to whoever is guessing.

*First sighting is recorded in the manager, not a success handler.* Four mechanisms would
mean four success handlers; every request passes authorization exactly once.

*Keys are `(provider, principal)`.* Approving `alice` from the internal store must not admit
`alice` from Google.

[#identity]
== Who is waiting

The key is stable and unreadable — for an OIDC login it is the `sub` claim, a long number.
Approving on that alone is deciding about a stranger, so `PrincipalIdentity` is captured at
*first sighting* and carried alongside:

[cols="1,3"]
|===
| `displayName` | a human name, or absent
| `email` | the address claimed, or absent
| `emailVerified` | whether the provider says it *verified* that address — or absent, when it says nothing
| `subject` | the stable identifier the key is built from
|===

Three states for verification, never collapsed into two. An unverified address is a claim
somebody typed, not something the provider stands behind; treating it as identity means
trusting whoever asserted it rather than the provider. "The provider said nothing" is a third
answer again, and pretending otherwise would make the queue look more informative than it is.

It is captured at first sighting rather than read live because the queue has to render for a
principal who is no longer signed in.

== Approving grants roles

Approval is not only "may this principal in". A federated sign-in arrives with
`OIDC_USER` and a `SCOPE_*` per scope and *no* `ROLE_` at all, so without this an approved
user clears the gate, reaches the application, and is refused by every `hasRole(...)` rule
in it — while an internal account has had roles all along, from configuration. The two
mechanisms were not equivalent in what they could express, and the federated one needs it
more.

So the decision carries them:

[source,java]
----
void decide(ApprovalKey key, ApprovalStatus outcome, String approver, List<String> roles);
----

[source,yaml]
----
uniauth:
  approval:
    default-roles: [ USER ]   # granted when an approver approves without naming any
----

The `ROLE_` prefix is added if absent, so an approver types `ADMIN` and `hasRole("ADMIN")`
matches. They are granted on the request *after* the decision, which is the same promise the
gate itself makes — approval takes effect without a second sign-in.

NOTE: This is why a `GrantedAuthoritiesMapper` bean cannot do the job. It receives the
authorities and not the principal, and roles are stored per principal, so it has nothing to
look them up by. The authorities are attached by a filter that has both.

The authentication is rebuilt to carry them, keeping its concrete type: that type is how
`MechanismResolver` knows which provider answered, so flattening every principal into a
`UsernamePasswordAuthenticationToken` would quietly break the approval key on the next
request. A type UniAuth does not recognise is left exactly as it was.

== The store

`ApprovalStore` is an SPI, and the gate is the only stateful thing in the library. That is
deliberate: owning a table would force Spring Data, a schema and migrations onto every
consumer.

[source,java]
----
public interface ApprovalStore {
    ApprovalStatus statusOf(ApprovalKey key);
    ApprovalRecord recordPending(ApprovalKey key, PrincipalIdentity identity, AuthProviderType mechanism);
    List<ApprovalRecord> list(ApprovalStatus... statuses);
    Optional<ApprovalRecord> find(ApprovalKey key);
    void decide(ApprovalKey key, ApprovalStatus outcome, String approver, List<String> roles);
    void remove(ApprovalKey key);

    default List<ApprovalRecord> pending() {
        return list(ApprovalStatus.PENDING);
    }
}
----

`decide` takes the roles the approver granted because a federated principal has none of its
own: an approval granting nothing admits somebody who is then refused by every `hasRole`
rule in the application. And a key the store has never recorded is *left alone* — creating a
record there would invent a decision about somebody with no identity and no mechanism behind
it. Admitting somebody before their first login is therefore `recordPending` followed by
`decide`; see xref:invitations.adoc#the-first-administrator[Who creates the first
invitation].

WARNING: `InMemoryApprovalStore` is the default and is *not production-fit*. It empties on
restart, taking every approval with it, and it is per-instance — two replicas do not agree.
Supply your own implementation for anything real.

=== Enumeration, and why it is not optional

`list` answers who the store holds. Pass no statuses for everything, or name the ones you
want:

[source,java]
----
store.list()                                        // everybody, oldest first
store.list(ApprovalStatus.APPROVED)                 // the access list
store.list(ApprovalStatus.PENDING)                  // the queue, same as pending()
store.list(ApprovalStatus.APPROVED, ApprovalStatus.DENIED)   // everyone decided about
----

Two rules an implementation has to honour:

* `ApprovalStatus.UNKNOWN` matches *nothing*, ever. It is the absence of a record rather
  than a value a record can carry, so a store must not treat it as a wildcard — an access
  list asking for the unknown would otherwise be handed every principal in the table.
* The ordering is `firstSeen` ascending, for the whole interface and not only for the
  queue, because `pending()` is published API that already promised oldest-first and now
  reads through `list`.

Overriding `pending()` stays supported, and is the right thing to do where a table is
indexed for the queue — that index should go on being used. The contract then checks the
two agree, because agreement is what drifts: change one query and not the other and
approved people appear on the approvals page, or waiting ones vanish from it.

[#migrating-to-list]
=== Migrating an existing store to `list`

`list` arrived after 4.1.0.3 and **breaks every implementation of this interface**. That is
deliberate, and the alternative was worse. A `default` method had nothing honest to return:
the store is the only thing that can enumerate itself, so a default could answer empty —
telling an access-review screen that nobody has access, which is a wrong answer rather than
a missing one — or throw, which turns a compile error into a page load at the moment
somebody opens the screen. A compiler error names the file and the method; neither of the
other two does.

What the gap was: `pending()` answers "who wants in" and by definition excludes everybody
already admitted, and `find` needs a key you already hold — which for an OIDC login is an
opaque subject claim nobody has memorised. So an application could build a queue but never
an access list: no way to see who can sign in today, what roles they hold, or who was
refused, and no way to pick somebody to revoke. The only route left was querying the
backing table directly, which couples the page to one implementation and leaves a non-SQL
store unable to offer the same screen at all (#10).

**The whole migration is one method.** For a JDBC store it is the query `pending()` already
runs, with the status predicate opened up:

[source,java]
----
private static final String SELECT = """
        SELECT provider, principal, display_name, email, email_verified,
               mechanism, status, first_seen, decided_at, decided_by, roles
        FROM uniauth_approval
        WHERE status IN (:statuses)
        ORDER BY first_seen ASC
        """;

@Override
public List<ApprovalRecord> list(ApprovalStatus... statuses) {
    // No filter means everything. UNKNOWN needs no special case: it is never stored,
    // so naming it simply matches no rows.
    List<ApprovalStatus> wanted = (statuses.length > 0) ? List.of(statuses)
            : List.of(ApprovalStatus.values());
    return this.jdbc.query(SELECT, Map.of("statuses", wanted.stream().map(Enum::name).toList()),
            ROW_MAPPER);
}
----

Then **delete your `pending()`**, or keep it if it rides an index — but if you keep it,
make sure it still answers exactly `list(PENDING)`.

WARNING: The mistake to expect is wiring `list` to the query `pending()` already used, so
that it answers only the queue. It compiles, it passes every test written before this
change, and the access list it exists for shows nobody. Three cases in the contract kit
catch it; nothing else will.

Already extending `ApprovalStoreContract`? Then the migration is checked for you — five new
cases cover enumeration, and `./mvnw test` is the whole verification. If you are not, this
is the release to start: see <<prove-your-implementation>>.

[#prove-your-implementation]
=== Prove your implementation

Because a real deployment supplies its own store, the rules it has to honour ship as an
executable suite rather than as prose (#37):

[source,java]
----
class JdbcApprovalStoreTest extends ApprovalStoreContract {

    @Override
    protected ApprovalStore createStore(Clock clock) {
        return new JdbcApprovalStore(dataSource, clock);
    }

}
----

It is in `uniauth-spring-boot-starter-test`, at test scope. The rule most worth having
checked is the one nothing else will tell you about: every authenticated request passes the
gate and records a sighting, so a store that overwrites on each one puts an approved
principal back in the queue on their second page view and loses the approver's roles with
it. The suite runs sixteen concurrent sightings against a settled decision to catch exactly
that. See xref:invitations.adoc#the-contract-kit[the contract kit] for the full story.

== Two things that bite if changed carelessly

* The pending page is added to the permitted matchers. Without that, the redirect loops.
* `PendingApprovalAccessDeniedHandler` only redirects requests the manager flagged, so a
  genuine 403 still looks like one. A *denied* principal gets 403, not the waiting page.
